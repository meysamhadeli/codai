# Configuration

Codai accepts YAML or JSON configuration, environment variables, and command-line
overrides. Use the settings palette for common edits and configuration inspection
when you need to understand which value is actually active.

## Find the active configuration

```bash
codai config paths
codai config settings
```

Inside a session, use `:config paths` and `:config settings`.
Inspection omits credential values and does not load plugin assemblies or start MCP servers.
`:settings` is an inspection alias, not the configuration editor.

## File discovery

`.codai.json` stores full runtime settings and optional discovery metadata together.
Discovery also reads `.codai.json` files in the shared home and bounded project
ancestors, but only the selected runtime configuration supplies provider and session
settings. A single project file can declare both:

```json filename=".codai.json"
{
  "theme": "graphite",
  "ai_provider_config": {
    "provider": "ollama",
    "model": "qwen3-coder"
  },
  "additionalDirectories": ["../shared-repository"],
  "skillDirectories": ["./custom-skills"],
  "mcpConfigFiles": ["./tools/mcp.json"]
}
```

Paths are relative to the declaring file; absolute paths and `~/` with an explicit
home scope are supported. Each list accepts at most 32 distinct paths. Metadata is
limited to 64 KiB, accepts JSON comments/trailing commas, and must be an object.
Invalid metadata is rejected rather than partially loading integrations.
Ancestor walks stop at the nearest `.git` directory or worktree `.git` file, before
inherited home or filesystem root, and after at most 128 levels. Explicit home roots
remain valid. Symbolic links are resolved for discovery identity and deduplication.
This does not merge ancestor provider credentials or grant server execution consent.
See [skills](/skills) and [MCP](/mcp#manifest-discovery) for precedence and activation.

Codai searches the selected directory in this order:

1. `.codai.json` (preferred)
2. `.codai.yml`
3. `.codai.yaml`

An existing project configuration takes precedence over user-wide
`~/.codai/.codai.json`; the files are not merged.
MCP discovery is separate: user-wide MCP entries remain visible with project runtime
settings selected and require their own startup approval. See [MCP](/mcp#manifest-discovery).
Native MCP entries accept VS Code's `type` key as an alias for `transport`, with
`type` taking precedence when both are present. `type: "http"` uses streamable HTTP.
User settings can also contain a VS Code-style named `servers` object; imported
entries still require checklist selection before connection. `gallery` and `version`
are informational metadata, not automatic installation instructions.
After workspace trust, interactive `codai` or `codai code` creates an empty
`~/.codai/.codai.json` before starting a session when no user configuration exists,
even if valid project settings are present. Existing JSON or YAML user settings are
left unchanged; project settings and credentials are not copied into the new file.
Without a usable saved connection, first-run setup still prompts for appearance and
connection settings. Cancelling appearance keeps the empty file; cancelling
connection setup preserves any saved appearance. Neither starts chat.
`--config-dir` / `CODAI_CONFIG_DIR` redirects this configuration directory.
Configuration basenames from earlier releases are no longer discovered or written.
Rename existing settings to `.codai.json` (or the matching YAML equivalent).
Unknown discovery fields are preserved when the settings editor saves changes.

| Option | Selects |
| --- | --- |
| `--config <path>` | An explicit configuration file |
| `--config-dir <path>` / `CODAI_CONFIG_DIR` | Configuration discovery scope |
| `--cwd <path>` | The project working directory |
| `--data-dir <path>` / `CODAI_DATA_DIR` | Isolated conversation, task, and transcript state |

Selecting a configuration directory does not move your project.

## Selection storage

Codai manages MCP and skill selections separately from runtime configuration in
`~/.codai/state/customization.json`. Use `/mcps` and `/skills` to update checks;
neither manager adds selection fields to `.codai.json`. The state directory follows
`--config-dir` / `CODAI_CONFIG_DIR`, not `--data-dir`, and is independent of the
selected project runtime settings.

| Section | Stored state |
| --- | --- |
| `mcp` | Per-project server selections, each with `enabled` and a definition `fingerprint` |
| `skills` | Per-project `enabled` and `disabled` skill-name arrays |
| `skillDefaults` | Global default skill exclusions |

Project keys are SHA-256 hashes of canonical, platform-normalized workspace paths.
The managers generate these keys; selections from one project do not enable servers
or override skill checks in another. MCP state remains private and definition-bound:
project files cannot grant imported-server startup consent. MCP credentials are not
copied into selection entries.

MCP and skill updates share a serialized, atomic merge path for the same filesystem
and canonical state file. Existing `customization.mcp`, `customization.skills`, and
`customization.skillDefaults` sections in user-wide `.codai.json` migrate when
catalogs load, including during offline configuration inspection. Private state is
saved before those sections are removed; provider settings, MCP definitions, and
unrelated fields remain in runtime configuration. An empty `customization` wrapper
is removed, but unrelated customization fields are preserved. Credentials are not
copied into the state file.

Existing private choices win conflicts. MCP records retain their fingerprint and
enabled flag together, while project skill choices and global defaults remain whole.
Valid private legacy `mcp-approvals.json`, global `skills.json`, and project
`.codai/skills.json` also migrate and are deleted only after successful state saves.
Malformed state is not overwritten or deleted. Selection files and JSON migration
sources redirected from their canonical user-directory paths are rejected; moving
selection state does not grant workspace-controlled MCP consent.

The state file retains a 64 KiB limit. Failed, cancelled, or oversized state saves
leave source settings intact; failed source cleanup can be retried after state was
saved. YAML-only runtime settings can remain YAML: selection saves do not create
a competing `.codai.json`. SDK hosts without global storage retain project-only
skill selection files. `UserCustomizationSettings.GetFilePath` exposes the managed
state path to SDK hosts.

## Override order

From lowest to highest priority:

1. Built-in defaults.
2. Selected configuration file.
3. Mapped environment variables.
4. Command-line flags.

Mapped environment overrides are `PROVIDER`, `MODEL`, `BASE_URL`, `API_KEY`,
`API_VERSION`, `TEMPERATURE`, `REASONING_EFFORT`, `MAX_TOKENS`, `THEME`,
`CHECKPOINTS_ENABLED`, `CHECKPOINT_RETENTION`, `PLAN_PROVIDER`, `PLAN_MODEL`,
`AGENT_PROVIDER`, and `AGENT_MODEL`.

Nested configuration also accepts double-underscore environment paths, such as
`AI_PROVIDER_CONFIG__STREAM=false`, `AI_PROVIDER_CONFIG__API_KEY`, and
`BUDGET__MAXTOKENS=100000`. Nested overrides are applied after the short mapped
names, so avoid setting both spellings for the same value.

`CODAI_CONFIG_DIR` selects configuration storage rather than a runtime option.
`CODAI_DATA_DIR` selects durable session state and `CODAI_HOOKS_DIR` adds a hook
manifest directory; their corresponding CLI flags take precedence.
`CODAI_ICONS=unicode` changes terminal glyph rendering only; it is not saved by the
settings editor. See [icons and fonts](/usage/terminal#icons-and-fonts).

A saved value may not become effective while an environment variable or flag overrides it.

## Settings reference

The provider fields below live inside `ai_provider_config`. Other keys are at the
document root unless a section is shown. Provider/model defaults come from the
[provider catalog](/providers#supported-providers).

| Key | Default or behavior |
| --- | --- |
| `theme` | Graphite; one of the ten supported terminal themes |
| `version` | Configuration metadata; does not install or select a Codai executable version |
| `ai_provider_config.provider` | `openai` |
| `ai_provider_config.model` | Provider-specific default; Azure uses your deployment ID |
| `ai_provider_config.base_url` | Provider endpoint unless overridden |
| `ai_provider_config.stream` | `true` |
| `ai_provider_config.temperature` | Unset: provider default; supported range 0 to 2 |
| `ai_provider_config.reasoning_effort` | Unset: provider default; `low`, `medium`, or `high` where supported |
| `ai_provider_config.max_tokens` | `0`: provider default; a positive value limits generated output, not the context window |
| `ai_provider_config.api_key` | Optional plaintext credential; prefer environment-based credentials |
| `ai_provider_config.account` | Opaque reference created by ChatGPT account setup; tokens are stored separately |
| `ai_provider_config.api_version` | Optional provider version metadata |
| `plan_provider`, `plan_model` | Optional Plan-mode provider/model overrides |
| `agent_provider`, `agent_model` | Optional Agent-mode provider/model overrides |
| `auto_compact_window` | `0`: model-derived automatic window; explicit values must be at least `32000` |
| `checkpoints_enabled` | `true`; disabling stops new snapshots, not access to existing ones |
| `checkpoint_retention` | `10`; at least 1 |
| `disabled_tools` | Empty list; exact tool names withheld from advertisement and execution |
| `plugins` | Empty list of additional native .NET assembly paths |
| `disabled_plugins` | Empty list of plugin paths withheld from composition |
| `mcp.servers` | Empty list of native MCP definitions; see [MCP configuration](/mcp#configuration) |
| `budget` | Per-request token, estimated cost, tool-call, and consecutive-failure controls below |

### Request budgets

These are stop conditions based on observed usage, not provider-side billing caps.
Token and cost usage can arrive only after a provider call has spent resources.
Unknown pricing cannot provide a reliable dollar limit. See [pricing limitations](/providers/pricing).

Use these exact nested budget key spellings when writing a file directly:

```yaml
budget:
  MaxTokens: 100000
  MaxCost: 2
  MaxToolCalls: 60
  max_consecutive_tool_failures: 3
```

`MaxTokens` and `MaxCost` default to `0` (unlimited). `MaxToolCalls` defaults to
60 effective calls per request; an unset or nonpositive configured value uses that
default. `max_consecutive_tool_failures` defaults to 3 and must be at least 1;
`--retries` overrides it. These counters restart for each task. They are separate
from the model output limit and automatic-compaction window.

## Example

```yaml
theme: graphite
ai_provider_config:
  provider: ollama
  model: qwen3-coder
  base_url: http://localhost:11434/api
  stream: true
checkpoints_enabled: true
checkpoint_retention: 10
auto_compact_window: 0
disabled_tools:
  - fetch_web
```

<Callout type="warning">
  Credentials saved by own-provider setup are plaintext. Do not commit secret-bearing
  configuration. Use environment-based credentials or a private configuration scope.
</Callout>

## Edit interactively

`auto_compact_window` is a token count: `0` uses the active model window, and
explicit values must be at least `32000`. `/autocompact` saves and applies this
setting immediately; `/autocompact 800k` saves `800000`. The model cap and reserved
headroom still apply. See [Context](/usage/context#choose-the-automatic-window).

Use `/settings` for the configuration editor. Ctrl+P or F1 opens the separate
settings action palette. Legacy section commands remain available:

```text
:preferences
:preferences provider
:preferences theme
:preferences mcp
:preferences plugins
```

Settings has no visible tab strip. Tab or Left / Right still switches
views; `/settings status`, `/settings usage`, and `/settings stats` open
them directly. Usage reports configured budget limits, not account quotas or
measured spending; Status and Stats report runtime policy and tool availability.

Choose a field, enter its value, then select **Save** or **Cancel**.
The editor uses the same numbered inline rows as other selection submenus,
aligns labels and known live values, updates displayed values
after a save during this workflow, and always hides credentials. **Edit...** means
the inspection context does not expose a value, not that no saved value exists.
The minimal borderless search band matches Settings. Known configuration values have a
tick; hidden or unknown values are not marked as configured. Theme and enabled
integration choices also show ticks, independently of the highlighted row.
Edits validate values, preserve unrelated YAML/JSON fields, and use atomic writes.
If no file exists, the editor creates `.codai.json` in the configuration directory.

| Setting | Save behavior |
| --- | --- |
| Provider, endpoint, credential, default model | Persisted for next startup |
| Theme | Persisted, then applied to this session and future sessions |
| MCP / plugin availability | Persisted; restart to rebuild connections |
| Session model, mode, approval toggle | Immediate session-only change; not a saved configuration edit |

Theme choices are **Graphite**, **Ocean**, **Azure**, **Violet**, **Magenta**,
**Forest**, **Mint**, **Ember**, **Sunset**, and **Coral**. Selecting one does not
preview it. Cancel, Escape, or failed persistence keeps the active theme unchanged.
First-run theme onboarding is different: choosing a theme saves it before connection setup.

The session model selector applies immediately on Enter and has no Save confirmation.
Use `:preferences provider` or `codai auth` when you want a saved model default.

## Manage integrations

```bash
codai config mcp disable local-tools
codai config mcp enable local-tools
codai config plugin disable path/to/ProjectPlugin.dll
```

Enable, disable, and remove mutate only entries in an existing configuration.
They do not install packages, delete plugin binaries, or restart external services.
See [MCP](/mcp) and [Plugins](/plugins) for setup and trust boundaries.

## Organize project guidance

Configuration controls runtime settings. [Project instructions](/customization/instructions),
[skills](/skills), and [custom commands](/customization/commands) describe how Codai
should work; none of them grants permissions blocked by runtime policy.

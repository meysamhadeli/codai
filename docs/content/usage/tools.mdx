# Tools

Tools connect a model response to real work: reading a file, applying a patch,
or running a test. You describe the outcome; Codai selects from the tools allowed
by the current mode, configuration, and approval policy.

```text
Find the parser for configuration files, add a regression test for an empty
model name, and run the relevant tests. Keep unrelated files unchanged.
```

## Inspect available tools

From your shell:

```bash
codai config tools
```

Inside a session:

```text
:config tools
```

Configuration inspection does not start MCP processes or load plugin assemblies.
External tools are discovered separately when needed, so offline inspection is not
a live inventory of every remote capability.

## How tool calls run

Codai advertises built-in tools allowed for the current request with their input
schemas. MCP schemas load on demand through request-local `tool_search` metadata
discovery; see [automatic MCP selection](/mcp#automatic-selection). When the model
requests an actual tool call, the shared runner applies these gates:

1. Resolve the tool and enforce the request's tool-access policy.
2. Check repeat, total-call, and task budgets.
3. Validate arguments against the tool's advertised JSON Schema.
4. Apply any guidance that requires the model to reconsider the call.
5. Request approval when required, then run the pre-tool hook.
6. Execute the tool, bound its output, and report its outcome.
7. Run the post-tool hook and capture a checkpoint when configured for a successful mutation.

The provider loop returns tool results to the model so it can correct arguments,
choose another tool, or answer. Streaming and non-streaming requests use the same
execution gates. Calls remain serial; read-only does not imply concurrency safety.

File reads, writes, edits, and structured patches review newly applicable or changed
[scoped instructions](/customization/instructions#request-and-file-scopes) before
approval or execution. This review does not grant permission or consume write approval.

Host and plugin file tools can implement `IFileTargetTool.GetTargetPaths` to
participate in scoped review. Standard `path` and `paths` fields have a default
implementation; structured tools supply their parsed targets. `IToolGuidance`
supports asynchronous discovery while retaining its synchronous default fallback.

`fetch_web` reads a known URL; it does not search for pages. Research guidance prefers
relevant offered MCP discovery and documentation/search tools, then URLs from actual
sources or the user. HTTP failures report their status and source with recovery
guidance, without automatically retrying, bypassing access restrictions, or treating
error pages as evidence. Consecutive failure limits remain unchanged.

### Argument validation and recovery

Shared validation applies to built-in, plugin, and MCP tools invoked through the
runner. It checks the advertised contract, including nested objects and arrays,
required fields, enums, numeric limits, composition, and local schema references.
Arguments must be a JSON object. Schemas without a declared dialect use JSON
Schema draft 2020-12; extra properties are rejected only when the schema forbids
them. Values are not coerced and defaults are not inserted.

Invalid arguments produce bounded feedback with JSON Pointer field locations
before approval or execution. The model can submit a corrected call. Invalid
attempts still consume call budgets and count toward the consecutive-failure
limit, so repeated mistakes cannot create an unlimited repair loop. Invalid
schemas and unresolved external references stop execution; validation never
downloads referenced schemas. Bundle dependencies into the tool schema using
local definitions instead.

Repeat detection ignores object key order at every nesting level, equivalent
JSON string escapes, and tool-name casing. Array order and string values remain
significant. These checks complement tool-specific path, content, and permission
checks; passing schema validation is not authorization.

## Files and search

These tools are read-only and available in Plan and Agent unless disabled.

| Tool | Purpose | When it helps |
| --- | --- | --- |
| `list_files` | List project files | Understand a directory before opening files |
| `glob` | Find paths by glob pattern | Locate test files or a named implementation |
| `grep` | Search text in project files | Trace a setting, error message, or symbol |
| `read_file` | Read numbered text, optionally by range | Inspect code and cite exact lines |
| `git_status` | Inspect working-tree state | Identify existing changes |
| `git_diff` | Inspect Git differences | Review edits without changing Git state |
| `git_log` | Read recent history | Understand prior changes |

`read_file` accepts one path or up to 20 paths sharing an output budget. Its default
is 2,000 lines per file, with a 5,000-line ceiling and a 5 MB file-size limit.
Large results should be narrowed with paths and line ranges, not repeatedly read in full.

`git_diff` accepts `source`: `working` (default), `staged`, `commit`, or `branch`.
Commit and branch comparisons require `target`; branch mode compares
`target...HEAD`. Targets must be simple refs or hashes of at most 256 ASCII
letters, digits, `/`, `-`, `_`, and `.`, without a leading option or `..`.
Revision expressions such as `HEAD~1` are not accepted; resolve a commit hash
instead. Git external diff/text conversion drivers are disabled. Each call has
a 30-second timeout and a 60,000-character output limit. Untracked files must be
identified with `git_status` and read separately. These read-only tools remain
available in Plan mode unless disabled by policy.

## File changes

| Tool | Purpose | Requirement |
| --- | --- | --- |
| `write_file` | Create or replace a text file | Agent and write approval |
| `edit_file` | Apply a targeted text edit | Agent and write approval |
| `apply_patch` | Add, update, or delete files through a patch | Agent and write approval |

Existing files must be readable within the 8 MB editing limit before replacement,
patching, or patch deletion. Failed reads do not authorize an overwrite.

Edit steps show actual added and removed line counts. Expand a step to review
per-file counts and a bounded diff. If a multi-file patch fails partway through,
the failed result reports changes that already reached disk; it is not an atomic rollback.

## Commands and verification

| Tool | Purpose | Requirement |
| --- | --- | --- |
| `run_command` | Execute a command in the project | Agent, shell access, and approval |
| `dotnet_build` | Run `dotnet build` and return compiler diagnostics | Agent, shell access, and approval |
| `dotnet_test` | Run .NET tests and return results | Agent, shell access, and approval |

Builds and tests can write artifacts, so they are not read-only operations.
Disable all three with `--no-shell`.

<Callout type="warning">
  Commands run with your user's privileges. Review the exact command and working
  context before approval. Tool policy is not an operating-system sandbox.
</Callout>

## Research and interaction

| Tool | Purpose | Boundary |
| --- | --- | --- |
| `fetch_web` | Retrieve readable content from a public HTTP(S) page | No private-network URLs, binaries, or embedded credentials |
| `ask_question` | Ask you for clarification | Requires interactive input; headless runs cannot invent an answer |
| `task` | Delegate a bounded investigation | Read-only context; no nested delegation |
| `submit_task` | Return a structured task outcome | Reports an outcome; does not itself edit files |

`fetch_web` is a page reader, not a browser or search engine. It does not execute
scripts or load page subresources; retrieved text is untrusted data.
Delegation spends model tokens even though it cannot write files.

## Skills

| Tool | Purpose |
| --- | --- |
| `skills` | Load an available skill's instructions |
| `read_skill` | Load a selected skill's instructions |
| `read_skill_resource` | Read a resource from a skill |

Skill instructions guide a workflow; they do not enable tools blocked by mode or policy.
Agent prompts list checked skill descriptions first and use `read_skill` to load
relevant instructions rather than injecting all checked bodies.
See [Skills](/skills) to create and invoke a reusable workflow.

## Limit tool access

Hide and block a named tool for a single run:

```bash
codai --disable-tool fetch_web --disable-tool run_command
```

Use `disabled_tools` in [configuration](/customization/configuration) for persistent
exclusions. `--no-sub-agents` disables delegation; `--no-shell` disables command tools.
Names must match Codai-facing tool names, including prefixes for [MCP tools](/mcp).

## Extend the tool set

- [MCP servers](/mcp) add capabilities from local processes or remote endpoints.
- [.NET plugins](/plugins) register tools in the host process.
- [Permissions](/usage/permissions) still govern external tools; installing a tool
  does not grant consent to execute it.

# Sessions and recovery

Conversation history, saved task metadata, and workspace files are different
things. Continuing a chat does not mean restoring files, and stopping a response
does not undo completed edits.

## Follow up after an interrupted response

If a model exchange fails or is cancelled, Codai retains your request and any
streamed response text in conversation history. The retained response is marked
as interrupted, not as a completed answer. This history is included in the next
request and saved with the conversation.

For example, after asking whether WSO2 supports correlation IDs, you can follow up
with "Use Context7 to research it" even if the previous lookup stopped at a tool
failure limit. The model receives the earlier question without requiring you to
repeat it. A follow-up starts a new request with its usual tool budget; it does not
automatically retry failed calls or change approvals. Failed and cancelled tasks
keep their original status.

## Continue your latest conversation

From the same project:

```bash
codai code --continue
```

Use `--data-dir <path>` when you need an isolated state directory.
Changing `--config-dir` selects configuration, not the project root or state directory.

## Branch or start fresh

Use `/session` to browse saved conversations from the main screen. `/sessions`
remains an accepted alias. Interactive terminals also offer
[session tabs](/usage/terminal#session-tabs) for quick navigation between open
conversations, with separate histories, modes, transcripts, and drafts.

| Command | Result |
| --- | --- |
| `:session fork` | Archive history and create an independent conversation branch |
| `:session new` | Archive history and clear conversation and active token counters |
| `:session history` | Browse up to 100 recent saved tasks |
| `:session restore` | Choose a saved task, checkpoint, and restore scope |
| `/session open` | Save the current conversation and open an empty tab |
| `/session next` / `/session previous` | Switch between open tabs |
| `/session close` | Save and close the active tab without deleting its history |

Fork and new require explicit consent. Starting fresh does not change workspace
files or the session's tool policy.

Continuing a task from history creates a new branch without overwriting the saved
source. The terminal restores the latest 20 turns for display; full saved history
remains available to the conversation.

Open tabs are maintained for the current process, not restored as a window layout
on restart. Use `/session` to reopen saved conversations. Tabs share workspace files
and tool policy; changing tabs never restores a checkpoint or grants new permissions.
Requests run in the active tab only; interrupt or finish one before switching.

Custom hosts can implement `IUserInterface.SetSessionTabs` to present the open-tab
list and restore their own active conversation view. Returning `false` retains the
ordinary conversation-replay fallback; noninteractive hosts need not implement it.

## Find a saved task

```text
:task history parser
:task show <task-id>
:task resume <task-id>
```

Resuming a task conversation and restoring checkpoint files are separate actions.
Inspect the task and current working tree before choosing a recovery scope.

## Checkpoints

Codai takes a workspace snapshot before each task and after its changes.
Snapshots exclude `.codai` state and are stored with the task.

The CLI reuses a project-scoped shadow Git repository and index across new tasks,
rather than initializing and indexing a separate repository on every request.
Each checkpoint retains its own revision and task/conversation metadata. Existing
per-task repositories remain supported. Capture, restore, and compare share an
exclusive repository lease; waiting for another process is bounded and cancellable.

<Callout type="warning">
  Git-backed CLI snapshots include binary files and honor Git ignore rules.
  Ignored local files and `.codai` state are preserved during cleanup, but ignored
  files are not backed up. SDK hosts using the text-only fallback do not receive
  binary backups. Restore can replace project files. Commit or separately back up
  important work, inspect the checkpoint, and review the scope before confirming.
</Callout>

<Steps>

### List snapshots

```text
:task checkpoints <task-id>
```

### Choose the scope

```text
:task restore <task-id> <checkpoint-id> files-only
```

| Scope | Workspace files | Captured task metadata |
| --- | --- | --- |
| `files-only` | Restored | Unchanged |
| `task-only` | Unchanged | Restored |
| `files-and-task` | Restored | Restored |

Older checkpoints without captured task metadata support `files-only` only.

### Confirm the restore

Restore requires explicit confirmation, even with automatic tool approval enabled.
File-only restore keeps the current conversation. Conversation restore through
`:session restore` continues in an independent branch.

</Steps>

## Control snapshot overhead

Checkpoints are enabled by default, with a default retention of ten.
Use `checkpoints_enabled: false`, `CHECKPOINTS_ENABLED=false`, or `--no-checkpoints`
to stop new capture. Existing checkpoints are not deleted.

```text
:task storage
```

Inspect retained checkpoint count and storage size without printing checkpoint contents.

## Export metadata

```text
:task export <task-id> <path>
:task import <path>
```

Export/import covers task metadata only. It does not transfer conversation history
or restore workspace files. Do not treat it as a complete session backup.
